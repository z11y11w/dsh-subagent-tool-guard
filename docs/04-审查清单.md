## B. 设计决策（我替你做的判断，可以否决）

- [ ] **B1** 判据用 `origin` 而不是 `delegationDepth`
      理由：`origin` 是 DSH 自己文档里指定的"分类字段"；`delegationDepth` 作为兜底也写了注释。
      代价：冷恢复的旧会话如果没有 `origin` 就不被限制（安全方向偏"放松"）。

- [ ] **B2** `allow` 用**差集**（preset 视角 − 全局视角），不是手写清单
      好处：免疫"将来全局层新增工具"。
      代价：见 `docs/03` N2/N3。

- [ ] **B3** 失败一律**放行**（catch 后不限制），不 fail-closed
      理由：宁可漏限制一个子 agent，也不能让插件把别人的派发搞崩。
      如果你要"更严"，这是唯一需要改语义的地方。

- [ ] **B4** Team 队友默认一起限制（`restrictTeamMembers: true`）
      依据：`dsh-agent-team/src/index.ts:65` 明说 teammates 是 subagent。
      如果你更在意 Team 可用性 → 改成 `false`。

- [ ] **B5** 施加时机是 `agent/created` **并 await**
      目的：子 agent 的第一个 step 就看到正确工具表（不会"先跑一步再被收走"）。
      代价：极端情况下派发会慢一点（`docs/03` N4）。

- [ ] **B6** 不提供"按需展开工具"的能力
      理由：那需要 `tool_list` 之类让模型自己开锁的入口，与"严格白名单"直接冲突。
      省 token 不在本插件的职责范围内（两者可以共存，见 `docs/03` 第四节）。

- [ ] **B7** 提供一个只读报告工具 `subagent_tool_report`
      理由：设计初稿 §3.5 的防呆要求。挂在全局层，主 agent 可见、子 agent 被挡。
      不想要就 `registerReportTool: false`。
