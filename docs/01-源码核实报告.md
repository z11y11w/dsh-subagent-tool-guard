# 01 · 源码核实报告

- 核实时间：2026-11-15
- 核实对象：本机在跑的 **DSH 0.2.2-rc.3**（Desktop，profile `<profile>`）
- 安装锚点：`<DSH_INSTALL_DIR>/`
- 方法：直接读 `app.asar` 内随包发布的 `src/*.ts`（Desktop 的 asar 用普通 `cat`/`grep` 读不了，用 `tools/` 下的 asar 探针脚本 + Host 文件读取工具）

**这一节的存在意义**：设计初稿里 §3.8 明说了「本方案依赖一个尚未验证的假设，验证不通过就必须改用显式 allow 列表」。本报告就是去验证它——**结论是那个假设不成立**。下面是逐条对账。

---

## 1. 一句话结论

> **`restrict({ allow: [] })` 不能用作「子 agent 只留 preset 工具」的实现。**
> preset 的行挂在一个**独立 standing scope** 上，对 agent 而言属于"继承来的"，
> 所以 `allow: []` 会把 preset 自己声明的工具一起挡掉，把子 agent 变成哑巴。
>
> 替代实现：**显式算出 `preset 视角工具名 - 全局视角工具名`，用它作 `allow`。**
> 这条已在 `package/index.js` 里落地。

---

## 2. 逐条对账

### 2.1 `restrict()` 的性质 — **成立**

源码：`@deepseek-ai/dsh-tools/src/index.ts:162-189`

```ts
restrict(filter: ToolRestriction): () => void {
  const scope = scopeOf(this.ctx)
  if (scope === undefined) {
    throw new Error('tools.restrict() requires a scoped context (agent.ctx): …')
  }
  …
  const known = this.view(scope).restrictableNames
  const unknown = [...allow ?? [], ...deny ?? []].filter(name => !known.has(name))
  if (unknown.length > 0) throw new Error('tools.restrict() names unknown global tool …')
  return this.layers.effect(this.ctx, layer => layer.restrictions.append(compiled), …)
}
```

要点：

1. 必须在 scoped ctx（`agent.ctx`）上调用，否则抛错 ✅ 设计初稿说得对。
2. `allow` / `deny` 里的名字必须是 `restrictableNames` 里的，否则 **throw**（不是忽略）✅。
3. 返回值是 disposer，撤销这一条 restriction ✅。
4. 空数组 `allow: []` 不涉及任何名字 → 天然绕开 unknown 校验 ✅ 设计初稿 §3.2.7 ② 说得对。

### 2.2 `restrict` 到底作用于谁 — **成立，但后果和设计初稿的假设相反**

源码：`@deepseek-ai/dsh-tools/src/index.ts:199-227`

```ts
private view(scope?: ScopeKey): ToolView {
  const layers = this.layers.chainLayers(scope)   // global→…→scope，最远祖先在前
  const own = this.layers.peek(scope)             // 只是"这一层"
  const inherited = new Map(this.layers.global.tools.entries())
  for (const layer of layers) {
    if (layer === own) continue                   // ★ 把"自己这层"摘出去
    for (const [name, registration] of layer.tools.entries()) inherited.set(name, registration)
  }
  …
  for (const [name, registration] of inherited) {
    knownNames.add(name); restrictableNames.add(name)
    if (layers.every(layer => layer.admits(name))) visible.set(name, …)   // ★ 受 restriction 约束
  }
  if (own !== undefined) {
    for (const [name, registration] of own.tools.entries()) { … visible.set(name, …) }  // ★ 无条件可见
  }
```

⇒ **restriction 只过滤 `inherited`（全局层 + 祖先层）；`own`（该 scope 自己注册的）永远可见。**
设计初稿 §3.2.1 第 3 条「scoped registrations remain visible」✅ 成立。

**但关键在下一节：preset 的注册算哪一边？**

### 2.3 preset 的行挂在哪一层 — **挂在祖先 scope，是"继承来的"**

两处源码合起来看：

**(a) 每个 preset 有自己的 standing scope**

`@deepseek-ai/dsh-agent-preset-registry/src/index.ts:119-138`

`@deepseek-ai/dsh-agent-preset-registry/src/mount.ts:204-215`

```ts
export async function mountPreset(ctx, id, plugins): Promise<PresetMount> {
  if (scopeOf(ctx) === undefined) throw new Error('agent-preset: mounting requires a scope')
  …
  const mount = { presetId: id, fiber: ctx.fiber, tree, key: scopeOf(ctx) }
```

**(b) agent 只是把自己挂到这个 scope 下面**

`@deepseek-ai/dsh-agent-preset-registry/src/index.ts:281-290`

```ts
private join(ctx: Context, key: ScopeKey, generation: Generation): void {
  const binding = { parent: bindScopeParent(key, generation.key), generation }   // ★ agentKey.parent = presetKey
```

⇒ 从 `agent` 的视角做 `view(agent)`：`chainLayers` = `[global, …preset 层…, agent 层]`，`own` = agent 层，**preset 层落在 `inherited` 里**。

**结论：`restrict({ allow: [] })` 会把 preset 注册的工具一起挡掉。设计初稿 §3.8 的担忧成立，且比它说的更确定——不需要"反向证据"（第三方插件说明），DSH 自己的源码就是证据。**

### 2.7 DSH 内置的 `toolFilter` 能不能直接用 — **不能，它是冷恢复用的死路**

`@deepseek-ai/dsh-subagent/src/descriptor.ts:85` 的 `ContinuableSubagentDescriptorData.toolFilter` 看着像"官方给了子 agent 工具过滤"的入口。但追写入点：

`@deepseek-ai/dsh-subagent/src/manager.ts:344-351`

```ts
const descriptor = snapshotSubagentDescriptor({
  mode: 'continuable',
  provider: spec.provider,
  label: spec.label,
  …agentProvider/agentModel/agentReasoningEffort…

```

全仓搜索 `toolFilter` 只有三处产物：`descriptor.ts`（读/校验）、`child-agent.ts:218`（恢复时施加）、`manager.ts:1251`（从 descriptor 读出来传给 compose）。**新创建子 agent 时从来没有人写入它**，`SubagentStartRequest` 也不暴露它。

⇒ 结论：**不能依赖内置 `toolFilter` 给新子 agent 加限制。**（这一点设计初稿没提，容易让人以为有现成接口。）

不过它证明了一件重要的事：`applyChildOverrides()` 里就是 `childCtx.tools.restrict(composition.toolFilter)` —— **在子 agent 的 ctx 上 restrict 是 DSH 官方自己的做法**，我们的实现方向没错。

### 2.8 怎么读「某个视角有哪些工具」— **agent 对象本身就是 scope key**

这是本次核实里最有用的发现，它决定实现能不能做到同步、零依赖。

`@deepseek-ai/dsh-agent-loop/src/agent.ts:148`

```ts
this.scope = createScope(loopCtx, this)     // ★ key 就是 agent 对象本身
```

所以 `ToolsService` 的这几个 public 方法都能直接吃 `agent`：

| 方法 | 传 `undefined` | 传 `agent` | 传 preset 的 key |
|---|---|---|---|
| `definitions(scope?)`（index.ts:305） | 全局层视角 | 全局 + preset + agent 自己这层 | 全局 + preset |
| `schemas(scope?)`（index.ts:316） | 同上 | 同上 | 同上 |

旁证：第三方插件 `dsh-tool-manager` 就是这么用的 —— `dist/runtime.js:195-200`

```js
inheritedSchemas(agent) {
    const scopedTools = agent.ctx.get("tools");
    return scopedTools.schemas(agent);        // ★ 把 agent 当 scope 传
}
```

**但它不能直接给 `allow`。** 因为 `definitions(agent)` 里还混着"agent 自己这层"注册的工具，名字塞进 `allow` 会触发 2.1 第 2 条那个 throw。所以要么拿到 preset 的 key，要么过滤掉自家那层。

### 2.9 怎么拿 preset 的 scope key — **`agentPresets.acquireScope(id)`**

`@deepseek-ai/dsh-agent-preset-registry/src/index.ts:385-398`

```ts
async acquireScope(id?: string): Promise<{ key: ScopeKey } & AsyncDisposable> {
  const generation = await this.retain(id)
  let disposed = false
  return { key: generation.key, [Symbol.asyncDispose]: async () => { … generation.users--; await this.collect(generation) } }
}
```

- 是 public 方法（不是 `@Remote`，但同进程可直接调）✅
- 借出的是**该 preset 当前 revision** 的 standing scope key
- 用完必须 `Symbol.asyncDispose`，否则这个 revision 会被一直 retain（`collect()` 不回收）
- 参考用法：`dsh-tool-manager/dist/dsh.js:38-46` 就是 `acquireScope(id)` → `tools.schemas(lease.key)` → `finally` 里 dispose

⇒ 本插件的算法就有了依据：

```
allow = names(definitions(presetKey))  -  names(definitions())      // 差集
```

### 2.10 `agent/created` 的语义 — **成立，且会 await 监听器**

`@deepseek-ai/dsh-agent/src/runtime-types.ts:278-291`

> An entered agent is ready for per-agent initialization after factory setup.
> **Listeners run in order and are awaited before creation resolves.** AgentLoop holds queued input until all listeners finish.
> Disposal retains the scope and session until dispatch settles; listeners must not await `agent.whenIdle()` or their own owner's disposal.

⇒ 监听器返回 promise 时，creation 会等它跑完 ⇒ **子 agent 的第一个 step 一定看到限制后的工具表**（不会漏首步）。
⇒ 但不能在里面 await `whenIdle()`（本插件没有）。
⇒ `agent/disposed` 是 `emit` 模式（`:292-300`），同步、不 await。

### 2.11 「未来新增工具」与「插件晚加载」— 两条必须各自处理

- **未来新增**：`restrict` 的 `allow` 是编译期 `new Set(allow)` 的固定快照。差集算法的好处是：**将来全局层新增的工具不在 allow 里 → 自动进不来** ✅ 白名单语义成立。
- **插件晚于 agent 加载**（HMR / 重启恢复）：`agent/created` 只对将来生效，已有 agent 不会触发 ⇒ **必须补扫 `ctx.agents.list()`**（`dsh-agent/src/index.ts:588` 提供 `list(): Agent[]`）。设计初稿 R2 成立，已实现。
